# 评审结论

> **总体判断**：两份文档是一套面向"平台级 Agent 产品"的责任框架，不是本项目的路线图。
> 最大价值是提供了一份系统责任检查表——约 1/3 ForgeAgent 已覆盖（印证方向正确），
> 约 1/3 已按候选顺序落地（副作用安全、终态语义、MCP 渐进披露、结构化 handoff 与 Rewrite 门禁实证），
> 剩余 1/3（浏览器平面、桌面宿主、Pet、Skills 供应链、权重治理）与"轻量优先"使命冲突，明确不借鉴。

## 一、对文档本身的评审

### 优点

- **证据纪律好**：区分事实/推断/预测，固定 SHA 快照，项目自报数据标注为"项目方主张"——与本项目 spec.md 的"实证汇报"要求同构。
- **抽象层次对**：8 个责任域（Goal / Loop / Memory / Identity / Sandbox / Verifier / Effects / HITL）和十项跨框架契约不绑定技术栈，作为设计检查表长期有效。
- **可验收**：规划文档把概念转成了验收指标（"100% 任务有停止证明"、"未知状态可识别并暴露"），格式与本项目 MILESTONE_GUIDE 的验收红线写法兼容。

### 缺点（相对本项目而言）

- **规模错配**：规划 M7–M10（浏览器能力平面、CLI+Gateway+GUI 三入口、Skills 供应链治理、权重来源治理）是给 Vercel / Cloudflare / 模型公司量级的产品写的，照搬直接违反本项目"轻量优先"宪法。
- **与本项目进度重叠**：文档 M1"可信完成骨架"（Goal 契约 + 终态机 + checkpoint + 事件日志 + 停止证明）已由本项目 M21 Loop Engineering 基本交付——`LoopRunner` 有 durable checkpoint、三类预算（wall_clock / token / max_rounds）、9 种 `LoopStopReason` 终态、resume、audit 事件流。
- **小瑕疵**：规划文档 frontmatter 的 `companion_doc` 指向 `2026-07-15-...`，实际文件名是 `2026-07-29-...`，引用失配。

## 三、建议纳入下一轮技术规划的借鉴清单（按优先级）

### P0 —— 副作用安全（已完成，保留为后续审计基线）

对 ForgeAgent 最切中要害：code-as-action 意味着生成代码和 MCP 调用都会产生真实副作用。
M29 之前的缺口已由归档 `external-action-receipts` change 补齐；本节现在用于说明基线边界，
不是新的执行令。

借鉴内容（已实现范围）：
- approved non-read-only MCP action 落**收据（receipt）**进 audit 事件流；
- Loop resume 遇到未决收据时以 `external_action_pending` fail closed，显式 resolve 后才继续；
- 远程 API、消息、支付、FileWrite、Exec、Edit 和 WebFetch 不在该 change 的收据范围内。

实现边界：不引入分布式幂等框架——audit 事件流就是现成载体，改动集中在
`loop.py` resume 路径和 `mcp_manager.py` 调用包装。

### P1 —— 终态语义补齐 + 注意力协议最小版（已由 M29 完成）

M29 已将 `needs_input` / `blocked` 作为注意力投影与既有执行终态分离，并由 HTTP headless
服务公开 `running / needs-input / blocked / ready` 附加状态；旧 `needs_info` 保留兼容。

### P1 —— MCP 工具渐进披露（已由 M30 完成）

M30 已将首轮 MCP 上下文收敛为有界目录，并提供只读 `MCPDescribe` 按需读取当前 discovery 的
有界 description/schema；既有调用、确认、receipt 和 CLI 完整清单语义保持不变。

### P2 —— Collaboration / Loop handoff 结构化移交（已由 M31、M40 完成）

M31 已把协作移交清单落为 host-owned、严格冻结、可重建的 `HandoffPacket`，覆盖已验证事实、
未决假设、公开副作用收据、停止条件和结果返回责任人。M40 将 Loop 迭代间 handoff 收敛为
宿主拥有的 `completed_items`、`open_questions` 与 `summary`，旧字符串只读兼容迁移；模型不能改写
goal、权限、预算或恢复语义。

### P2 —— 流程纪律、Memory 治理与 Rewrite 实证（M32 建立，M41-M43 应用）

1. **"每条长期 prompt 指令都要有退出条件，模型升级即删过时脚手架"**——写进 spec.md 或
   MILESTONE_GUIDE，作为 Jinja2 提示词模板的维护纪律；
2. **"Memory 设计四问"**（谁能写 / 什么是真相 / 何时失效 / 崩溃后以哪份恢复）与
   **"重写决策门槛（六项量化指标）"**作为未来相关提案的评审门。

M41 已按六项门槛完成一次真实 CLI 重构：性能、可靠性、维护成本、兼容性、团队能力、
迁移/回滚风险均有同口径基线和终值，未新增依赖。该证据只证明 M41 合格，不自动授权未来重写。

M42 已将 Memory 四问落实为运行时契约：持久化记录的 source/writer/truth/visibility/复核/恢复/
纠错字段由宿主拥有，旧 v1 只能只读加载或经精确 manifest 显式迁移。真实 readiness 为 `no_data`，
因此只验证迁移能力，没有制造历史数据或声称生产数据迁移成功。

M43 已归档，并对 Python 执行路径完成了六项独立测量。最终 trusted 中位数为 `0.010625 ms`，restricted
中位数为 `108.947834 ms`、吞吐为 `9.077731 ops/s`；正常执行均为 20/20，worker crash 和 timeout
后均可继续执行，且临时哨兵证明失败 block 没有重放。container 在本机为 `not_available`，团队维护演练为
`not_ready`，最终 verdict 为 `keep_python`。这些证据否定当前启动 Rust 重写的必要性，不否定未来
在真实越阈、同机复测、团队能力和回滚门禁同时满足后另立可回滚的单模块试验。

## 四、明确不借鉴及理由

| 项目 | 理由 |
| --- | --- |
| 文档 M7 浏览器能力平面 | ForgeAgent 是 CLI + headless HTTP 的轻量 agent，浏览器平面是另一个产品形态 |

| 文档 M10 权重来源治理 | 属于模型发布方责任 |
| 语言分层路线（Rust/Zig 重写） | 项目已定 Python + uv；文档自己的"重写决策门槛"恰好是反对动它的理由 |
