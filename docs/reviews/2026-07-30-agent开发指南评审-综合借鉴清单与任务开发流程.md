## 3. 关键契约建议

### 3.1 外部副作用收据

适用对象是可能影响系统外部状态、且调用方无法立即获得权威结果的动作。建议最小记录如下：

```text
action_id       稳定动作 ID
idempotency_key 幂等键（若目标系统支持）
action_type     动作类型
target          目标系统/资源
request_digest  脱敏后的请求摘要
attempt         尝试次数
phase           prepared | dispatched | confirmed | unknown
checkpoint_id   关联 checkpoint
evidence_ref    权威回执或查询证据
timestamp       状态变更时间
```

语义约束：

- `prepared` 只表示动作已准备，不能表示外部系统收到。
- `dispatched` 表示已发出，但还没有足够证据证明结果。
- `confirmed` 必须绑定权威回执、查询结果或可复核证据。
- `unknown` 表示进程或网络在发出与确认之间丢失了确定性；它不是普通 `failed`。
- 从 `unknown` 恢复时只能执行查询、幂等确认、补偿或人工决策，禁止按原请求无条件重放。
- 对不支持幂等或查询的目标，必须在动作前给出风险提示和停止条件；不能伪造 exactly-once 保证。

### 3.2 终止与注意力状态

建议把运行结果和注意力状态分开表达：

- 运行结果：`succeeded`、`failed`、`cancelled`。
- 注意力状态：`running`、`needs_input`、`blocked`、`ready`。

`ready` 表示任务已有可消费的结果或下一步，不等价于 Loop 已成功；`needs_input` 和 `blocked` 必须携带原因、责任方、所需输入/动作和恢复条件。现有 `needs_info` 保留兼容读取，但新协议不再用它混淆用户输入、外部确认和系统阻塞。

### 3.3 MCP 渐进披露

第一阶段只做目录化和按需展开：

1. 首轮上下文提供工具名、短描述、权限、风险等级和调用入口。
2. 模型明确选择工具后，再取得参数 schema、示例和错误说明。
3. 展开、调用、拒绝和错误均写入审计；外部副作用动作同时写收据。
4. 先对 token、延迟和工具选择准确率做基线，再决定是否需要更多缓存或新的发现 API。

不在这一阶段引入 Code Mode（此处泛指由 MCP 提供、在隔离运行环境中执行组合代码的模式；本项目暂无此依赖）、Worker 或新的复杂代理层。

## 4. 任务开发流程

### 阶段 0：分发边界与工作区确认

每个任务开始先确认：

- 包索引发布、正式 tag、远程 push 和发布自动化不在当前路线图；本流程只验证本地工程产物。
- 阅读 `milestones/latest` 指向的里程碑、`ACTION_PLAN.md`、`spec.md` 和相关 OpenSpec/Comet 状态。
- 检查工作区脏改动，明确哪些是用户已有改动；不得回滚或覆盖。
- 原 `publish-v0-1-0` 已撤销并移入日期归档，仅作为历史审计证据；不提供恢复路径。

### 阶段 1：基线与重复建设检查

把需求写成一页问题卡：

```text
问题/用户影响：
现有能力与证据：
缺口及信任边界：
不在范围内：
候选方案与最小方案：
成功/失败/阻塞/需输入退出条件：
验证器、测试数据和回滚方式：
```

先用现有实现、测试、里程碑和 CodeGraph 定位复用点。若只是补文档、补测试或不改变行为的单文件调整，可直接执行；否则进入 Comet 门禁。

### 阶段 2：任务分级与范围门禁

| 类型 | 处理方式 |
| --- | --- |
| 纯问答、评审、文档或一行无行为调整 | 直接处理，完成后做文档/格式校验 |
| 已有行为的局部缺陷 | 使用 hotfix；若涉及状态契约、安全边界或多模块，升级为完整流程 |
| 单一模块、边界清晰、可回滚的轻量能力 | 使用 tweak；先写契约和最小测试。例如：某一工具增加可选参数且默认保持既有行为，或 CLI 增加 `--dry-run` flag |
| 新能力、跨模块改动、外部副作用、安全/权限、状态模型变化 | 使用完整 Comet/OpenSpec 流程 |
| 需求扩大、出现第二个独立目标或需要改变发布计划 | 暂停当前任务，请用户选择继续当前 change 还是拆分新 change |

### 阶段 3：契约与设计

设计必须回答：

1. 谁拥有状态，谁可以推进或撤销状态？
2. 哪些操作跨越信任边界，失败后是否可能产生外部副作用？
3. 如何区分失败、需输入、阻塞和结果未知？
4. 旧客户端/旧协议如何兼容，何时删除兼容层？
5. 证据来自哪里，什么情况下只能声明“部分完成”？
6. 如何恢复、补偿、回滚和防止重复执行？

设计阶段完成后，等待用户确认 proposal/design/tasks、技术设计、执行模式、TDD/direct、分支/worktree 等 Comet 决策点；未确认不得把候选清单当作执行授权。

### 阶段 4：实现

- 先建立失败或边界测试，再写最小实现；非平凡逻辑必须保留可运行验证。
- 遵循 Ponytail 阶梯：YAGNI、标准库、现有 helper/依赖优先；新增依赖、抽象层、配置面或大 diff 必须说明必要性。
- 并行只用于互不共享状态、文件边界清晰的子任务；共享状态契约由一个负责人整合。
- 新 Prompt/Skill 同时提交退出条件、最小回归集和失败反馈格式。
- 新外部动作同时提交收据状态、幂等/查询策略和未知状态恢复测试。

### 阶段 5：验证与证据

按风险从小到大执行：

1. 定向单元/契约测试。
2. 状态恢复、权限边界、恶意输入和重复执行测试。
3. 相关模块集成测试与全量 `pytest`。
4. `ruff`、构建和 OpenSpec/Comet 严格验证。
5. 在真实边界上验证：明确区分 Mock、真实 provider、Docker/Linux、远程服务和未验证场景。

失败时原样记录关键输出，使用 systematic debugging；不得用“应该可以”替代证据，也不得把未运行的真实边界测试写成已通过。

### 阶段 6：评审、里程碑与收尾

- 先处理代码评审发现，再给出变更摘要。
- 文档、测试、验收证据和回滚说明必须与实现同步。
- 只有实现、验证和验收完成后，才更新里程碑文件与 `milestones/latest`；候选顺序本身不改变 `ACTION_PLAN.md`。
- Comet change 按 verify → 用户确认 → archive 收尾；外部发布不属于当前路线图，不能由“代码完成”自动触发。
- 任何“完成”表述必须明确区分本地/RC 工程验证与外部公开分发；本项目当前不执行后者。
