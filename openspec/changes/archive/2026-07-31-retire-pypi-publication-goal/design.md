## Context

当前唯一 active change `publish-v0-1-0` 尚有 4/9 任务完成，剩余任务全部围绕人类候选实践、PyPI 上传、正式 tag、远程 push 和发布证据。M30-M37 的核心能力已独立完成，但每个里程碑仍重复引用“发布继续暂停”，造成路线图和历史记录混淆。

## Goals / Non-Goals

**Goals:**

- 建立单一、可检索的分发边界：包索引发布、正式 tag、远程 push 不属于当前路线图。
- 把 `publish-v0-1-0` 从 active changes 迁入带取消说明的历史归档目录。
- 让 M30-M37、ACTION_PLAN、评审清单、治理规范、RC 文档和离线测试互相一致。

**Non-Goals:**

- 不删除 M28 的 RC 验证证据，不声称已经公开发布。
- 不改变 clean-wheel、CLI、HTTP 或协作 smoke 的工程验证能力。
- 不设计替代分发渠道，也不恢复任何外部发布流程。

## Decisions

1. **采用“撤销并归档”而非删除 active change。** 删除会损失 4/9 任务的历史上下文；归档目录增加取消说明即可保留证据，同时让 `openspec list` 不再把它当作 active 目标。
2. **历史事实与路线图分离。** M28 RC 文档保留“当时未发布”的事实，但将正式发布阻塞条件改为“当前路线图已移除”，避免出现“另行授权后恢复”的暗示。
3. **以离线文档契约测试做回归门禁。** 测试只读取文本和目录状态，断言 active release change 不存在、撤销归档存在、canonical 文档声明分发目标已移除；不执行网络或发布命令。
4. **不改运行时代码。** 这次问题是规划生命周期和术语一致性问题，增加运行时抽象会扩大范围且没有验收收益。

## Risks / Trade-offs

- [历史引用仍指向旧 active 路径] -> 在归档说明中保留原 change 名，并在规划文档中统一使用“已撤销归档”措辞。
- [未来有人误把 RC 当正式版] -> RC 和正式发布说明都新增“历史工程记录/不在当前路线图”的显式声明。
- [测试过度依赖中文措辞] -> 断言稳定的语义标记和归档目录状态，避免检查完整段落。

## Migration Plan

1. 创建本 change 的 delta specs、更新规划文档与离线契约测试。
2. 将 `publish-v0-1-0` 的未完成任务改为“取消/不适用”并移动到日期归档目录，附带撤销说明。
3. 运行文档专项、OpenSpec strict、Ruff 和相关测试；失败时只修正文档或测试契约。
4. 归档本 change；不执行任何外部发布动作。

## Open Questions

- 无。若未来重新考虑公开分发，应建立全新的独立 change，并重新进行范围、威胁模型和验证评审；本 change 不提供恢复路径。
