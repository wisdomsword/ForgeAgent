## Context

M45 已归档三个顺序 change，并把最新里程碑指针更新为 `milestone_045.md`。借鉴评审文档仍将 M44 声明为当前基线；现有 canonical spec 和测试也只允许 M44，因此文档漂移会被旧断言固化，而不是被发现。

## Goals / Non-Goals

**Goals:**

- 让借鉴评审文档、`milestones/latest` 和 M45 证据保持一致。
- 让未来完成里程碑能够更新基线，而无需重写“必须是 M44/M45”的永久规范。
- 保留 M44 HTTP 审批、M43 Rewrite 基线、发布目标移除等历史事实和边界。

**Non-Goals:**

- 不改变 M39-M44 已交付的运行时能力。
- 不恢复 PyPI、正式 tag、发布自动化或公网 HTTP 控制面。
- 不把条件候选转换成自动承诺的后续里程碑。

## Decisions

1. 当前基线的权威来源是 `milestones/latest`；评审文档必须在 frontmatter 和正文中引用同一里程碑。
2. 能力交付仍使用具体历史里程碑记录，例如 M44 继续证明 loopback HTTP 动作审批，而 M45 只证明基线一致性和生命周期证据对账。
3. 测试解析里程碑编号并比较，不使用只检查“至少 M44”的宽松断言，也不把 M45 写成永久规范。
4. 发布目标移除和开发分支 push 的区分保持原契约，不因当前用户授权 push 而恢复分发路线图。

## Risks / Trade-offs

- [动态基线可能掩盖错误指针] → 同时验证目标里程碑文件存在、评审 frontmatter 和正文编号相等。
- [历史 M44 能力被误写成 M45 交付] → 文档明确区分当前基线与能力首次交付里程碑。
- [未来里程碑忘记更新评审文档] → 生命周期测试要求与 `milestones/latest` 精确一致。
